Strengths

应继续保持的工程决策

八项超出同类项目平均水平的工程实践，是后续演进的地基。

01

薄 route + 厚 lib 分层纪律

81 个 handler 大多是“鉴权 → 校验 → 调 lib → 统一错误”，业务按域前缀组织，模块图清晰、无上帝模块。

02

Prisma 单例设计精巧

dev 热重载复用、按 Prisma.ModelName 校验委托、构建期缺 DATABASE_URL 时返回不可用代理、连接池参数变化自动换池。

03

契约测试文化

缓存配置、API 错误格式、CSP、暗黑模式等横切行为均有契约测试兜底，防止重构破坏约定。

04

缓存失效机制完整

revalidatePublicContent 同时处理新旧 slug/分类/标签/系列的路径清理，少见的“写后精确失效”完整实现。

05

RSC 边界与 React 19 利用

首页 Promise.allSettled 局部降级、文章页 use() 消费 Promise、getPublicPostSelect() 统一数据形状。

06

安全细节的亮点

AI token 哈希 + scope + 吊销、模型 API key AES-256-GCM 加密入库、SQL 全参数化、IP 哈希、日志脱敏、timingSafeEqual。

07

数据模型索引充分

146 处索引/唯一约束覆盖列表查询、软删过滤、去重等热点，schema 是“想过的”。

08

部署链路稳健

先 migrate deploy 再起新容器、镜像预构建失败回退、零停机软链切换；CI 用独立 PostgreSQL 跑真实构建。

Findings

问题清单

按严重程度分级（P0 高风险高收益 / P1 中风险 / P2 长期项），每条附文件与行号证据，均经交叉核验。

P0 · 高风险 P1 · 中风险 P2 · 长期项
P0 高风险 / 高收益 —— 建议近期处理 6 项

P0-1表单与数据层缺少统一抽象（前端工程化债）

文档宣称“表单用 React Hook Form + Zod”，实际全项目仅 ContactForm.tsx 一处使用；lib/validation.ts 是手写校验层；登录/注册/文章编辑器全部手写 useState。
  • 客户端无请求库：无 SWR/React Query，admin/posts/page.tsx 单文件 1250+ 行整页 use client，15+ 状态内联
  • useInfinitePosts.ts 用 requestIdRef 手写防竞态
建议：① 引入轻量数据请求层（SWR 或基于 admin-api-client.ts 的 useApiQuery）；② 拆分巨型页面（hook + 表格/工具栏子组件）；③ 表单统一迁移 RHF+Zod，或修正文档承认手写校验层现状。

P0-2软删除 × 唯一约束冲突（数据模型级缺陷）

Post.slug、Series.slug、Category.name/slug、Tag.name/slug 均为 @unique（schema.prisma:152,213,691-692,705-706），软删只写 deletedAt。 软删后重建同名条目必然触发 P2002，用户只看到 409 “Conflict”，且无法与真冲突区分。
建议：① 迁移为部分唯一索引（WHERE "deletedAt" IS NULL）；② 或软删时改写 slug（追加 -deleted-<id>）；③ 至少把该场景的 P2002 映射为“该名称已被历史内容占用”的明确提示。

P0-3cron / internal 接口防护面薄弱（后端安全）

  • middleware.ts matcher 不覆盖 /api/cron 与 /api/internal（middleware.ts:119-121），保护全靠各 handler 自检
  • cron secret 是非常量时间比较（token !== configuredSecret），而 newsletter 已用 timingSafeEqual —— 同一目标两种实现
  • 内部日志密钥未配置时回退到 AUTH_SECRET（api-operation-log-ingest-secret.ts:6），会话签名密钥与内部接口密钥复用
建议：① 统一 crypto.timingSafeEqual；② 独立 OPERATION_LOG_INGEST_SECRET，去掉 AUTH_SECRET 回退；③ 纳入 middleware 统一防护或抽共享 requireInternalSecret()；④ 生产密钥缺失时快速失败而非静默降级。

P0-4生产安全基线：TLS / HSTS / CSP / Cookie（基建）

  • 依据 .env 与 CI 配置，NEXTAUTH_URL / NEXT_PUBLIC_SITE_URL 为 http；security-headers.ts 无 HSTS、CSP 无 upgrade-insecure-requests
  • auth-cookies.ts:5-16 在 http 配置下不给会话 cookie 加 Secure —— 若接入层未终结 TLS，会话 token 明文传输
  • CSP 实为 script-src 'unsafe-inline'（dev 加 unsafe-eval）、img-src http: https:，XSS 纵深防御被削弱
建议：① 全站 HTTPS（nginx/caddy 终结），同步把 URL 改为 https 使 Secure cookie 生效；② 安全头加 HSTS 与 upgrade-insecure-requests；③ 中长期用 nonce/hash 方案去掉 unsafe-inline，img/connect 收敛白名单。

P0-5密钥卫生（基建）

本地 .env 含真实生产密钥（DB/GitHub/七牛/DashScope）；AI_NEWS_CRON_SECRET 为可猜测的固定字符串；NEXTAUTH_SECRET 未替换为强随机值； .gitignore 只挡 .env（第 40 行），.env.local 等变体未被忽略。
建议：① 轮换全部真实密钥（cron secret 改强随机，半小时即可完成）；② .gitignore 改为 .env* + !.env.example；③ 把 auth-secret.ts 的占位符检测推广到其他密钥。

P0-6鉴权 / 校验 / 错误处理入口不一致（后端一致性）

  • bookmark 路由用 getServerSession 手写鉴权绕过 requireSession（bookmark/route.ts:19-25），丢失操作日志 actor 登记
  • api/posts/route.ts:30-35、api/posts/[slug]/route.ts:68-72,84-90 手拼 404/500 JSON，绕过 toErrorResponse
  • 全项目 18 处 console.error 吞错，无 requestId 贯穿（x-request-id 只在 middleware 拒绝路径存在）
建议：① 所有 route 统一走 requireSession + 语义化错误 + toErrorResponse；② 用 withApiOperationLogging 统一生成 requestId 并透出到错误日志。
P1 中风险 —— 建议中期处理 10 项

P1-1getBlogSettings() 无渲染级去重

44 处调用点；root layout 单文件调用两次（app/layout.tsx:44,94）、文章页 generateMetadata + 页面主体各一次——每页渲染 3~5 次相同 $queryRawUnsafe，仅靠 ISR 缓解。
建议：用 React cache()（或 unstable_cache）包裹，同一请求内去重，成本极低。

P1-2多套 UI 体系并存（前端）

components/shadcn/ui（60+ 组件）、自定义 components/ui、components/admin/ui、components/admin/primitives 四层共存；登录用自定义 Button/Input，后台用 shadcn 同名组件，视觉与行为割裂。
建议：定单一 shadcn 体系，逐步迁移自定义 ui/ 的少量封装，删除重复实现。

P1-3AI 新闻源抓取无超时 / 重试（后端可靠性）

runDailyAiNews 注入的 fetchImpl 就是裸 fetch（ai-news-run-flow.ts:569,619），ai-news-fetchers.ts 抓取路径无 AbortSignal。一个挂起的 RSS 源可让整次日报无限期卡住；GitHub Actions 轮询 45×10s 超时后，运行仍在服务器后台悬挂。同类：DashScope 轮询固定 24×5s 无退避。
建议：source fetch 统一加 AbortSignal.timeout(15~30s) + 有限重试 + 每源独立失败记录；轮询加指数退避。

P1-4浏览量双计（数据准确性）

viewCount 在两个入口分别 +1：客户端 analytics 信标（api/analytics/visit/route.ts:83）与详情 API GET（api/posts/[slug]/route.ts:75-78）。当前架构下文章页大概率同时触发两者，单次阅读浏览量 +2。
建议：明确唯一计数入口（建议只留 analytics 信标 + 去重），详情 GET 改为纯读；存量偏差可用 VisitLog 重建。

P1-5Markdown 渲染无显式 sanitize（前端安全纵深）

文章页与编辑器预览的 react-markdown 仅配 remark-gfm/rehype-highlight，无 rehype-sanitize、无 urlTransform（javascript: 链接过滤）、外链无 rel="nofollow noopener"。
建议：加 rehype-sanitize + 自定义 urlTransform + 外链 rel 处理；编辑器预览与正文共用同一渲染管线。

P1-6限流键可伪造 + 内存限流无淘汰（后端）

getRateLimitKey 直接取 x-forwarded-for 首个 IP（rate-limit.ts:128-132），若代理未清洗该头可伪造绕过；createMemoryRateLimiter 的 Map 无淘汰（生产默认走数据库驱动，风险降级）。
建议：在可信代理层统一覆写/丢弃非信任 x-forwarded-for；内存限流加定期清理或上限。

P1-7Docker 构建与 ISR / DB 依赖冲突（基建）

公共页 revalidate=300 会静态预渲染，文章页 generateStaticParams 触库（失败吞错返回 []）；但 Dockerfile 构建期只传 NEXTAUTH_URL/SITE_URL，无 DATABASE_URL——构建产物与 CI（带 DB）不一致，文章页在 Docker 构建下退化为纯动态。
建议：① 明确“构建期不触库”约定并文档化（CI 同步做一次无 DB 构建验证）；② 或改用 output: 'standalone' + 运行时 DB；③ generateStaticParams 显式注释退化行为。

P1-8环境变量文档缺失（基建）

.env.example 缺 AI_NEWS_CRON_SECRET、OPERATION_LOG_INGEST_SECRET、RATE_LIMIT_DRIVER、AI_MODEL_SECRET_KEY、DATABASE_POOL_MAX、NEXT_IMAGE_ALLOW_LOCAL_IP、NEWSLETTER_* 等十余项实际使用变量（已在代码中核验）。
建议：补齐并分组注释；可加契约测试断言“代码引用的 env 键 ⊆ .env.example”（符合项目测试文化）。

P1-9交互接口 check-then-act 竞态（后端）

bookmark/like 的 toggle 是“查存在→删除/新建”两步（bookmark/route.ts:40-64、like/route.ts:27-44），并发双击可产生 P2002（被兜底为 409）或双写窗口；点赞只绑 browserId 从未用 userId（like/route.ts:29-30），登录用户清 cookie 即丢赞。
建议：用 upsert/deleteMany 原子化或捕获 P2002 幂等处理；点赞对登录用户可绑定 userId（属产品决策，需确认有意为之）。

P1-10AI 任务计数 N+1 与串行重算（后端性能）

每完成一个任务 item 就调用 refreshAiTaskCounts 全量 findMany+update（ai-tasks.ts:330-352）；post-summary-jobs.ts:218-292 批量摘要串行且每篇重算——20 篇批量 = 20 次全表重算。
建议：完成时统一刷新一次，计数改为事务内 groupBy 原子重算；批量重算移出循环。
P2 低风险 / 长期项 9 项

P2-1E2E 覆盖极薄且不进 CI

e2e/ 仅 3 文件 4 用例（reader 浏览、author 重定向、admin 重定向），登录/评论/上传/AI 关键路径无覆盖；ci.yml 不跑 test:e2e。

P2-2死依赖未裁剪

embla-carousel-react、react-resizable-panels 及部分 shadcn 组件（carousel/resizable/menubar/hover-card）无业务调用。

P2-3viewTransition 全站生效

globals.css navigation: auto + 620ms 布局帧时长对 admin/auth 等交互页也触发；slug 派生的 view-transition-name 在同页重复 slug 时可能冲突。

P2-4后台两种数据模式并存

categories/tags/taxonomy/ai/settings 为 RSC 直查，posts/comments/ai-news/newsletter/series/topic-guides 为整页 use client 自 fetch——建议统一为“RSC 取数 + 客户端增强”，与 P0-1 合并推进。

P2-5工程门禁缺口

无独立 typecheck/Prettier 脚本与 .prettierrc；eslint 忽略 scripts/*.cjs；无 engines/packageManager 字段。

P2-6可观测性近乎空白

无 Sentry/APM/日志聚合，仅散落 console.error；建议至少接入 Sentry + 结构化日志（requestId 贯穿已在 P0-6 铺垫）。

P2-7构建产物未瘦身

非 standalone，runner 镜像装全量 prod 依赖并拷贝 src/tsconfig；recharts/react-markdown 等重型依赖未 next/dynamic 按需加载；CJK 字体（Noto Serif SC 700+900）首屏体积需评估子集化。

P2-8细节卫生

rate_limit_entries 是 schema 外裸表（仅存在于迁移 SQL，无 model），prisma db pull 或新成员维护时易产生认知错位；生产 IP 硬编码于 daily-ai-news.yml:20 等；dev 硬编码回退密钥（anonymous-actor.ts、api-operation-log-ingest-secret.ts:3）。

P2-9任务调度为进程内存态，多实例/重启不安全

日报 activeRuns Set（cron/ai-news/route.ts:9）与摘要任务队列（post-summary-jobs.ts:26,45）在进程内存中，重启丢运行态、多实例可重复执行；AiNewsRun.runDate 无 DB 唯一约束。扩缩容前需改为 DB 驱动状态机（status 状态机 + ON CONFLICT 守卫）。同层风险：taxonomy/posts 按关系 _count 排序，大表下慢查询。
Roadmap

优化路线图

按依赖关系与投入产出比排定的三阶段推进顺序。

Phase 1

安全与正确性

1~2 周 · 不依赖大重构
  1. P0-5 密钥轮换 + .gitignore 修正（半小时，立即做）
  2. P0-4 HTTPS + HSTS + CSP 收紧 + Secure cookie
  3. P0-3 cron/internal 防护统一
  4. P0-2 软删除唯一约束方案决策与迁移
  5. P1-4 浏览量单计数 + P1-6 限流键清洗
Phase 2

客户端工程化

2~4 周 · 收益最大的一笔投入
  1. P0-1 数据请求层（SWR）+ 巨型组件拆分 + 表单统一
  2. P1-2 UI 体系收敛 + P2-4 后台数据模式统一
  3. P1-1 getBlogSettings 加 cache()（半小时）
  4. P1-7 构建/ISR 契约文档化 + P2-7 动态加载与字体优化
Phase 3

可靠性与纵深

持续
  1. P1-3 新闻源超时/重试 + P1-9 原子化交互接口
  2. P1-5 Markdown sanitize + P0-6 错误/鉴权入口收口
  3. P2-1 E2E 扩充并入 CI、P2-5 门禁补齐
  4. P2-6 可观测性接入（Sentry/结构化日志）

⛔ 暂不建议做的事

  • 大改技术栈（换 ORM、换认证、迁移出 App Router）：当前核心链路健康，收益不抵风险。
  • 微服务 / 拆分部署：单实例 + 数据库限流对当前流量绰绰有余，先补监控再谈扩缩容。
