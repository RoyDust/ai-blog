# 前台重设计 · 第一阶段：首页三方案

- 日期：2026-10-20
- 状态：待选定方案（选定后进入第二阶段，按批次设计其余前台页面）
- 范围：仅设计产物，不含任何应用代码改动
- 线框图：已在会话中用 visualize 渲染（桌面端 + 移动端各一份），本文用文字与 ASCII 草图记录版面结构

## 1. 现状观察（2026-10-20，站点「依尘の博客」）

- 首页结构：浮动胶囊导航（`.reader-nav`）→ 城市夜景背景图淡入页面 → 编辑部式 Hero 卡（衬线 h1 + 站点描述 + 精选文章 + CTA + 右侧封面）→ AI 日报横条（5 条）→ 紧凑最新文章列表（4 条）。
- 左侧 rail（个人资料 / 分类 / 标签 / 热门 / 阅读统计）仅在 `xl` 以上出现，移动端完全没有这些入口。
- 暗色为默认主题；亮色模式下背景图仍然存在，整体偏灰。
- 字体：正文 AlibabaPuHuiTi-3-65 仅 500 一档字重；标题 Noto Serif SC 700/900 仅作用于 `.serif-display-scope` 内的 h1/.font-display。
- 色彩：OKLCH + `--hue`（默认 250）参数化整套 token，HuePicker 可改色相；改进分析文档已决定保留该体系。
- 数据：首页只取 `getHomeLatestPosts(5)` 与 5 篇 `generatedByAiNews` 文章；分类 / 标签 / 热门由 Sidebar 走 SWR 客户端请求。

## 2. 共同约束（三方案都遵守）

- ISR：公共页 `revalidate = 300`；`/` 已在 `lib/cache.ts` 的 `PUBLIC_LIST_PATHS` 中，文章 / 分类 / 标签 / 系列变更都会失效首页。若首页新增专题指南或系列查询，需确认对应写路径也调用了 `revalidatePublicContent`。
- 契约测试 `src/app/__tests__/public-layout-cache.test.ts`：公共 layout 不读 session，不新增 `(public)/loading.tsx`。登录态相关内容（阅读统计、收藏）不进首页。
- 内容来源只用现有数据：`getHomeLatestPosts`、`generatedByAiNews` 文章、`getCategoryDirectory`、`getTagDirectory`、系列查询、`listPublicTopicGuides`、热门（`viewCount` 排序）、`getPublicProfile`、`getBlogSettings`、NewsletterForm。
- 中文可读性底线：正文 ≥ 15px、行高 ≥ 1.65、段宽 ≤ 36em；标题行高 1.2–1.4；meta 不小于 12px。
- 触控目标 ≥ 44px；焦点样式可见；`prefers-reduced-motion` 下关闭位移动画。
- 中文全程；暗色 / 亮色 / 响应式 / 可访问性为验收项。

## 3. 方案 A 「编辑部」：杂志式多栏，信息密度优先

### 定位

把站点当一本每天出刊的技术杂志头版：报头、栏目条、头条 + 要点栏，首屏就能看到十条以上内容。适合「AI 日报每日更新 + 人工文章不定期发布」的节奏。

### 信息架构（自上而下）与数据来源

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 报头 | 站名（衬线大字）、日期、常驻搜索框、主题切换、账户 | `getBlogSettings`、现有 Navbar 动作区 |
| 栏目条 | 首页 / 文章 / 分类（下拉）/ 系列 / 专题指南 / 归档 / 关于 | 分类下拉：`getCategoryDirectory` |
| 头版 7:5 | 左头条：封面、分类、标题、摘要、日期、阅读时长、浏览量；右「AI 日报 · 今日要点」5 条（日期 + 去前缀标题） | `getHomeLatestPosts()[0]`；`generatedByAiNews` 最近 5 篇，复用 HomeAiDailyStrip 的前缀清洗 |
| 栏目带 | 分类 chips 带篇数 | `getCategoryDirectory` |
| 正文 8:4 | 左「最新文章」两列卡片 4 篇；右 rail：热门 3 篇、标签 12 个、Newsletter | `getHomeLatestPosts(5)` 后 4 篇；热门改为 server 查询；`getTagDirectory`；NewsletterForm |
| 系列 + 专题指南 | 并排两栏，各 3 条 | 系列查询（带篇数）；`listPublicTopicGuides` 前 3 |
| 页脚三栏 | 站点说明 / 栏目链接 / RSS 与订阅 | 现有 Footer 数据 |

不出现：阅读统计、收藏（登录态内容移到 `/profile`）。

### 关键交互

- 报头滚过 120px 压缩为单行 sticky（站名 + 栏目 + 搜索）。
- 搜索：桌面常驻输入框；移动端图标；`/` 快捷键聚焦。
- 卡片 hover：标题下划线从左展开 + 封面 1.02 缩放；焦点 2px 朱砂外框、2px 偏移。
- 区块：细线 + 栏目标题分隔，纵向节奏 2.5rem。
- 首屏 ISR 直出，无骨架；仅 Newsletter 表单是客户端组件。
- 移动端：报头单行；栏目条横向滚动；头条在上、要点在下；最新文章单列；热门 / 标签 / 系列 / 指南折成三组手风琴置于列表之后；订阅与页脚收尾。

### 权衡

- 优点：信息承载最强、出版物气质最明显、每日更新有固定露出位。
- 代价：对内容量敏感，栏目空了很难看；与现状差异最大——`reader-nav` 胶囊、`reader-shell` 背景图、玻璃 blur 在首页全部弃用，若全站统一，`reader-card` 等十余个类要改成线框式；`--hue` 被弱化，与改进分析「保留 OKLCH + hue」的结论冲突。
- ISR：首页新增分类 / 热门 / 标签 / 系列 / 指南 5 个 server 查询，都在 300s 内刷新；`/` 已在失效路径表内。
- 工作量：L。

## 4. 方案 B 「静读」：单栏极简，正文优先

### 定位

像一份独立作者的通讯：一栏、大量留白、没有卡片也没有背景图，层次全靠排版。读者来了就是读。适合「一周一两篇长文、AI 日报只作附带」的节奏。

### 信息架构与数据来源

| 区块 | 内容 | 数据来源 |
|---|---|---|
| 极简顶栏 | 左站名文字；右文章 / 系列 / 归档 / 关于 + 搜索图标 + 主题切换；透明、不隐藏、不 blur | 现有 Navbar 链接 |
| 开场自述 | 头像小图、tagline 作首句、bio 一段、links 一行文字链接 | `getPublicProfile` |
| 最近 | 8 条：左侧日期列、衬线标题、一句摘要、分类 + 阅读时长；无封面 | `getHomeLatestPosts(8)` |
| AI 日报 | 两行：最近一期日期 + 标题；往期 4 个日期链接 + 全部 | `generatedByAiNews` 最近 5 篇 |
| 系列 | 前 3 个：标题、篇数、前两篇文章名 | 系列查询 + 每系列 take 2 |
| 专题指南 | 前 3 条：标题 + 一句描述 | `listPublicTopicGuides` |
| 订阅 | 单行邮箱表单 + RSS 文字链接 | NewsletterForm |
| 页脚一行 | 版权 · 分类 · 标签 · 归档 · RSS | — |

分类 / 标签 / 热门不进首页，挪到 `/posts` 筛选区。

### 网格与排版

圆角只给控件 6px；无阴影、无 blur、无卡片边框；分隔只用 1px 细线 + 4rem 留白。

### 关键交互

- 顶栏常驻不收起，滚过 80px 出现底部细线。
- 搜索图标点开为行内输入框，`/` 聚焦，回车跳 `/search`。
- 列表项 hover 只变标题颜色 + 下划线偏移动画，不位移；焦点 2px 强调色外框。
- 区块间 4rem 留白 + 小号 kicker。
- 首屏全 server 渲染，无骨架；去掉首页 Sidebar 的 4 个 SWR 请求。
- 移动端几乎不变：顶栏链接收进汉堡菜单；日期列上移到标题之上。

### 权衡

- 优点：实现最省、性能最好、移动端天然最佳、可访问性最易达标；去掉背景图 / blur / motion layout 后首屏体积明显下降。
- 代价：信息密度最低，首屏只有自述 + 三四条文章；AI 日报 / 系列 / 指南露出最弱，站点的「AI 平台」属性几乎看不出来；视觉辨识度完全依赖排版，与其他页面的 `reader-*` 卡片体系割裂，第二阶段必须一并统一。
- ISR：不变。
- 工作量：首页 S，全站统一 M。

## 5. 方案 C 「信号台」：AI 内容产品型，模块化 bento

### 定位

把站点当作一个 AI 内容工作台：首屏是 bento 网格，头条、今日 AI 日报、站点脉搏并列；左侧窄导航 rail；顶部命令式搜索。暗色优先，完整保留 OKLCH + `--hue` 体系。适合「日报每天更新、文章每周更新」的混合节奏。

### 信息架构与数据来源

- 区块等距 1.5rem。
- 首屏全 server 渲染，无骨架；若指标改为客户端请求则需 4 格数字骨架。
- 移动端：rail 变底部 tab bar；bento 单列堆叠，顺序为头条 → AI 日报 → 最新文章 → 指标折成一行四个数字；搜索由顶栏图标打开全屏面板。

### 权衡

- 优点：与现有视觉体系最接近，`reader-card` / `reader-panel` / hue 系统都可渐进演化；AI 日报与指标放首屏，最能体现站点的 AI 属性；亮色独立调色能解决现状亮色偏灰的问题。
- 代价：新组件最多（rail、tab bar、cmdk 面板、bento 网格、指标卡）；首页 server 查询增至 7 个（其中 4 个 count 很便宜）；现有 Navbar 与新 rail / tab bar 要并存一段时间；md 断点（768–1024）需要单独定义 bento 的两列折叠。
- ISR：不变，count 查询随 300s 一起刷新。
- 工作量：M 到 L。

## 6. 自评（设计审视）

- A：头条与「今日要点」并列会分散头版焦点，需在实现时把要点栏降一档（更小字号、更淡色）；栏目空置时应自动隐藏区块而不是留白；弱化 hue 与既定决策冲突，若选 A 需在 ADR 里记录为有意覆盖。
- B：首页看不出 AI 平台属性，若站点定位仍是「AI 内容平台」则与品牌不符；换系统无衬线会让不同平台字形不一致（Windows 上为微软雅黑），这是零加载成本的代价。
- C：「站点脉搏」四个数字是否对读者有意义存疑（可能是虚荣指标），可改为「本周更新」时间线或直接去掉；rail 与底部 tab bar 使导航从一套变两套，第二阶段需要定义所有页面的 rail 行为；bento 在 md 断点容易拥挤。
- 三方案共性：都把登录态内容移出首页，符合 ISR 契约；都把搜索提升到首屏可达；都给 AI 日报固定位置（B 最弱）。

## 7. 对比表

| 维度 | A 编辑部 | B 静读 | C 信号台 |
|---|---|---|---|
| 定位 | 每日出刊的技术杂志头版 | 独立作者通讯，读为先 | AI 内容工作台 |
| 信息密度 | 高（首屏 10+ 条） | 低（首屏 4–5 条） | 中高（首屏 3 模块 + 6 卡） |
| 视觉风格 | 衬线 + 细线 + 暖纸色，无阴影无背景图 | 纯排版，单强调色，留白 | 暗色优先卡片网格，保留 hue 与微光 |
| 移动端表现 | 中：三组手风琴承接 rail 内容 | 优：几乎零改动 | 良：底部 tab bar + 单列 bento |
| 实现成本 | L（弃用 reader-* 体系，全站重排） | 首页 S / 全站 M | M–L（5 个新组件，token 可沿用） |

## 8. 推荐

推荐 **C 信号台**。理由：

1. 与站点真实节奏一致：AI 日报每天生成、人工文章每周一两篇，C 给日报固定首屏位且不要求多栏目同时供稿（A 的前提）。
2. 与既定技术决策一致：改进分析已决定保留 OKLCH + `--hue`，C 完整保留并顺带修正亮色模式偏灰；A 需要推翻这项决定。
3. 成本可控：token、`reader-card`、`reader-panel`、InViewReveal、cmdk 都能复用，新增工作集中在 rail / tab bar / bento 三件，可分 PR 落地。
4. 最能表达「AI 内容平台」定位；B 做不到这一点。

备选：若更看重出版物质感与最大差异化，且接受 hue 退居次级与 L 级工作量，选 A。B 只在站点定位回归「个人技术博客」时才合适。
