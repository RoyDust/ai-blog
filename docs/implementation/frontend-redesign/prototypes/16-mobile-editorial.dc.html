页面性能优化：先找到真正的瓶颈

凭直觉动手是性能优化最常见的误区。先用 Performance 面板录一次真实加载，再决定从哪里下刀。

正文 17px / 1.85，段距 1.25em；h2 衬线 1.5rem，h3 无衬线 700。手机没有 hover，不显示标题旁的 # 锚点。

性能优化最常见的误区，是在没有数据的情况下凭直觉动手：压缩一遍图片、加几个懒加载、换个更快的 CDN，然后发现首屏还是慢。问题不在于这些手段无效，而在于它们未必打在真正的瓶颈上。

这篇记录我在博客改版时的一次排查过程：先测量，再拆解，最后只改最贵的那一项。整个过程不需要任何付费工具，浏览器自带的面板就够用。

瓶颈为什么总在意料之外

我们对页面的直觉，往往来自开发机上的体验：本地网络快、缓存是热的、设备性能好。真实读者的环境完全相反，于是一个在本地几乎察觉不到的同步脚本，到了中端手机上就能把首屏推迟一秒以上。

先测量，再优化。没有数据支撑的优化，大多只是把慢换到了别的地方。
代码块：超长行在块内横向滚动（white-space: pre + overflow-x: auto），页面本身不横向滚动；画面里被块右缘截断的部分就是可滚动区。右上复制按钮 44px、透明。
假设 · 手机代码字号仍 .875rem，不缩小、不自动折行。

const ttfb = nav.responseStart - nav.requestStart;

// 2. 最大内容绘制
const lcp = await new Promise<number>((resolve) => {

字体：中文站点最容易忽略的大头

一套完整的中文字体动辄数兆字节。按页面实际用字做子集化、配合 font-display: swap，几乎不影响观感，却能省下首屏最大的一笔下载。
