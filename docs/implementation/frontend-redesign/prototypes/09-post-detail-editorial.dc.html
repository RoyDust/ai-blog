性能优化最常见的误区，是在没有数据的情况下凭直觉动手：压缩一遍图片、加几个懒加载、换个更快的 CDN，然后发现首屏还是慢。问题不在于这些手段无效，而在于它们未必打在真正的瓶颈上。

这篇记录我在博客改版时的一次排查过程：先测量，再拆解，最后只改最贵的那一项。整个过程不需要任何付费工具，浏览器自带的面板就够用。

#瓶颈为什么总在意料之外

我们对页面的直觉，往往来自开发机上的体验：本地网络快、缓存是热的、设备性能好。真实读者的环境完全相反，于是一个在本地几乎察觉不到的同步脚本，到了中端手机上就能把首屏推迟一秒以上。

先测量，再优化。没有数据支撑的优化，大多只是把慢换到了别的地方。

#先录一次真实的加载

打开 Performance 面板，把网络节流设为「快速 4G」、CPU 降速 4 倍，再录一次冷启动。如果想把关键指标留存下来，可以直接在页面里读取：

TypeScript 
// 1. 首字节时间
const [nav] = performance.getEntriesByType('navigation') as PerformanceNavigationTiming[];
const ttfb = nav.responseStart - nav.requestStart;

// 2. 最大内容绘制
const lcp = await new Promise<number>((resolve) => {
  new PerformanceObserver((list) => {
    const last = list.getEntries().at(-1);
    if (last) resolve(last.startTime);
  }).observe({ type: 'largest-contentful-paint', buffered: true });
});

console.table({ ttfb, lcp });

#把指标拆到具体资源

首字节和最大内容绘制之间的那段时间，才是前端真正能掌控的部分。在瀑布图里按开始时间排序，把阻塞渲染的样式、同步脚本和首屏大图逐一标出来，通常一眼就能看到哪一项最贵。详见 关键渲染路径 的说明。

#从最贵的一项开始

这次排查的结论有点出乎意料：拖慢首屏的不是图片，而是一个在头部同步加载的统计脚本，加上两套没有子集化的中文字体。前者改成延迟加载，后者按页面实际用字裁剪，首屏时间就从 3.4 秒降到了 1.6 秒。

#字体：中文站点最容易忽略的大头

一套完整的中文字体动辄数兆字节。按页面实际用字做子集化、配合 font-display: swap，几乎不影响观感，却能省下首屏最大的一笔下载。

下一篇会讲怎么把这些指标接进日常监控，让退化在上线当天就被发现。
