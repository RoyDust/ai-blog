## 2. 逐项方案

### P2-01：部署必须等待应用 readiness

**入口与原因**

[远程部署脚本](../../scripts/deploy/deploy-remote.sh)只检查容器运行状态，循环耗尽没有失败出口；末尾镜像清理允许失败，最终退出码不能证明应用可用。[生产 Compose](../../docker-compose.prod.yml)尚无 healthcheck。

**实施方案**

1. 按 Issue #7 增加无鉴权、无缓存的 `GET /api/health/live` 与 `GET /api/health/ready`。live 只验证处理器可响应；ready 只验证 Web 必需配置和共享 Prisma 客户端的一次轻量数据库读。
2. 配置预检和 ready 共用一个窄的纯解析器。复用现有数据库地址解析和认证密钥占位符规则，校验两个站点 URL 为绝对 HTTP(S) URL。脚本不再维护另一份必填键数组。预检在候选镜像准备后、迁移和替换服务前执行。
3. 数据库检查预算固定为 2 秒。数据库或配置异常返回 503，成功返回 200；响应仅含通用检查结果，不泄露环境变量名、值、主机、SQL 或堆栈。检查超时后须限制遗留查询的资源占用，不能仅超时响应而放任探针查询累积。
4. 两个健康端点明确豁免操作审计写入。live 不依赖数据库；ready 不通过审计隐式增加第二次数据库操作。
5. app healthcheck 使用镜像已有 Node 调用 ready：间隔 10 秒、探针超时 3 秒、启动宽限 20 秒、失败阈值 3 次。无需为探针安装 curl，不改变重启策略。
6. 部署仍最多观察 12 次，间隔 5 秒。只有 `healthy` 成功；`starting` 等待；`unhealthy`、退出、服务缺失、健康状态不可读或超时均非零退出。成功摘要与原有成功后的镜像清理仅在健康门禁通过后执行。
7. 失败输出仅保留有界、脱敏的状态和近期日志。保留失败现场，沿用现有人工回退流程。

**验收**

- 配置缺失、占位密钥、非法 URL 均在迁移和服务替换前失败；有效配置进入后续步骤。
- 数据库不可用时 live 仍为 200，ready 为 503；ready 查询超时在预算内结束。两者均 `no-store`，不写审计日志。
- 假 Docker 测试覆盖 `starting → healthy`、立即 healthy、持续 starting、unhealthy、退出、缺失和不可读状态；只有 healthy 返回 0。
- 校验 Compose 配置，并用生产镜像验证数据库断连对健康状态的影响。

**发布边界**

本项无数据库模型迁移，不引入 worker 健康、遥测平台或自动回滚。应用已执行数据库迁移时，切回旧镜像不等于数据库回滚；人工回退须先确认 schema 兼容。

### P2-02：AI 自动应用与成功状态原子提交

**入口与原因**

[ai-batch-jobs.ts](../../src/lib/ai-batch-jobs.ts)先调用 `markAiTaskItemSucceeded`，再调用 [ai-post-actions.ts](../../src/lib/ai-post-actions.ts) 的 `applyPostAiTaskItem`。前一步可能更新父任务计数与完成通知，后一步才写文章。崩溃后，终态任务项被恢复扫描跳过。

现有 `applyPostAiTaskItem` 只接受 `SUCCEEDED` 项，且文章更新与任务项标记分两次提交。因此不能只交换这两个调用的位置。

**目标不变量**

| 场景 | 允许对外展示的结果 |
| --- | --- |
| 仅生成建议，或该动作不在自动应用白名单 | `SUCCEEDED / applied:false`，输出可供人工应用 |
| 开启自动应用且动作在现有白名单 | 文章写入与 `SUCCEEDED / applied:true` 在同一提交中可见 |
| 自动应用未完成 | 不能先向计数、通知或 UI 宣告成功 |
| 输入已过期、文章已删除或目标字段已被人工修改 | 不覆盖文章；按冲突原因结束该项并保留诊断信息 |
| 父任务首次进入终态 | 最终计数、站内完成通知及本次事务确定的接收人一起提交；提交前均不可见 |

**实施方案**

1. 外部模型调用留在数据库事务之外。生成完成后构造字段更新，复用当前动作解析和校验，不扩大自动应用白名单。
2. 提取可在事务中使用的文章应用逻辑。自动应用入口接受活动任务项与本次生成结果；人工应用入口继续要求已有成功建议。两个入口共享字段更新逻辑，各自保留权限与状态前置条件。
3. 在同一事务中读取并验证任务归属、任务项状态、文章软删除状态及生成输入快照。用行锁或条件更新保证检查和写入不可被并发修改穿透；明确检查受影响行数。正文、目标字段或相关归属变化时拒绝旧结果。不要仅依赖事务外的 `findUnique` 检查。
4. 原子写入文章、任务项输出、`applied`、`status`、`finishedAt`，并更新 [ai-tasks.ts](../../src/lib/ai-tasks.ts) 管理的父任务计数与终态。多个完成路径按相同顺序锁定同一父任务，避免丢失聚合更新和锁顺序冲突。
5. 父任务首次由活动态进入终态时，在同一事务中写入站内通知和接收人。复用 [notifications.ts](../../src/lib/notifications.ts) 的通知数据及管理员接收人规则，将相关数据库操作改为显式接收同一个事务客户端，不能在事务内调用仍使用全局 Prisma 的写入辅助函数。保留 `ai-task:${taskId}:${status}` 去重键及 `(notificationId, userId)` 唯一约束。这里的“提交后通知”指提交后才对外可见，不是在提交后再创建通知。
6. 通知、接收人或最终聚合写入失败时，整笔事务回滚，文章、任务项和父任务均不能部分成功。此类持久化失败保留活动项供现有恢复路径重试，不落入外层 catch 后另行标记业务 FAILED；未来 Worker 接入后由既定平台处理重试。模型错误或输入冲突仍按已有业务状态处理，其最终计数与通知也必须同事务提交。
7. 进程在事务提交前退出：任务项仍是可恢复的活动项，可以重新生成并尝试提交。提交后退出：文章、终态、通知及接收人已经一起保存；重入直接跳过，不重新生成、不补发、不改写通知，也不向此后新增的管理员补接收人。外部模型已返回但事务尚未提交的崩溃窗口允许再次调用模型。
8. 仅生成建议和人工应用也验证事务、幂等与聚合行为，避免共用函数改造破坏原路径。人工应用已成功建议时不再次触发父任务完成通知。冲突项采用已有 `SKIPPED` 并附原因；实际业务执行错误采用已有 `FAILED`，不新增产品状态。

**缓存刷新与终态恢复的分工**

- 公共缓存刷新仍在事务提交后执行。可捕获的刷新失败单独记录 taskId、受影响路径和错误，不把已提交的文章或任务改为失败。进程在提交后退出可能来不及记录错误，因此不承诺仅靠日志自动重放。
- 新增窄的管理员维护入口 `POST /api/admin/ai/tasks/[id]/revalidate`（拟新增），使用 `requireAdminSession`、语义错误和操作日志包装器。它在 Next.js 请求上下文中，根据该任务已应用项、输入快照及当前文章计算路径，调用既有缓存辅助函数；缺失可恢复的旧路径信息时明确报告，不能伪报全部刷新成功。
- 该入口允许对终态任务重复调用，但只刷新缓存，不执行模型、不应用输出、不更新任务状态或通知。无需重新把终态任务排入执行器，也不增加 Outbox、队列任务或完成阶段状态。
- 未人工重试时沿用现有 300 秒 ISR 再验证机制：过期后的访问会尝试重新生成；后台再验证失败可能继续提供旧内容，因此 300 秒不是恢复成功的时限保证。正常任务完成仍立即尝试失效缓存。

**历史数据与规格边界**

- 先列出 `SUCCEEDED / applied:false` 项，再结合原任务的 apply 配置、动作白名单和输入快照判别。正常建议不能视为损坏记录，不能批量自动应用所有历史建议。
- 确认属于自动应用遗漏的项须重新校验当前文章；可安全应用者按新事务处理，输入已过期者保留原记录并重新生成。历史输出缺少足够归属证据时交人工判定。修复聚合计数时避免再次发出原完成通知。
- 本项修复业务提交边界，可先于 #11/#8 完成。持久化调度仍由 #11 提供、#8 接入，保持一个 AiTask 对应一个队列任务。
- 本方案沿用现有状态与通知表，不增加输出检查点、执行代次或自建队列。终态短路与 #8 保持一致；通知已随业务提交，不依赖重投终态任务来补发。若后续要求崩溃后复用尚未提交的模型输出，应单独修改规格；#8 当前明确排除这类检查点。

**验收**

- 在模型返回后、事务中、提交后且尚未刷新缓存时分别注入进程中断；重启后没有自动应用项永久停在 `SUCCEEDED / applied:false`。提交后中断的任务已经存在一条完成通知，每名本次接收人恰好一条接收记录。
- 并发执行同一项、人工编辑目标字段、替换任务、软删除文章时，旧执行不能覆盖新数据。文章与项终态没有部分提交。
- 在通知或接收人写入处注入数据库错误，断言文章、项终态、父任务终态和通知全部回滚，活动项仍可恢复；恢复完成后文章仅应用一次，计数正确。事务提交前其他连接看不到本次通知。
- 多项任务的成功、失败、跳过计数正确；重复进入终态任务后，通知及接收人 ID、内容、已读状态和数量均不变，不因新增管理员而补发。无管理员时允许一条通知、零条接收记录。
- 注入缓存刷新错误，业务和通知仍保持成功；随后调用管理员维护入口刷新受影响路径。重复调用不改变文章、任务或通知。补测未登录 401、非管理员 403、任务不存在及部分路径刷新失败。
- `apply:false` 建议及不允许自动应用的动作仍可成功保留未应用结果。人工应用仍能工作。
- E18 以自动应用所需的全部业务结果完成为通过条件，不通过增加等待掩盖提前成功。

### P2-03：Newsletter 显式保存收件人集合与投递进度

**入口与原因**

[newsletter-campaigns.ts](../../src/lib/newsletter-campaigns.ts)边读取订阅者边投递。第一封已成功、第二封尚未尝试时退出，恢复会进入 `PARTIAL_FAILED`；重试只选 `failed` 投递，遗漏没有记录的订阅者，甚至把活动改成无法正常继续发送的 `FAILED`。

**实施方案**

1. 首次发送先在数据库中冻结本次符合条件的收件人集合，并建立完整的 `pending` 投递行，再开始外部发送。复用 `NewsletterDelivery` 的 `(campaignId, subscriberId)` 唯一约束。
2. 冻结集合和活动领取必须原子提交。建议增加活动级 `audienceFrozenAt` 以区分“已冻结且为空”和“尚未初始化”。大量收件人以数据库集合操作或同一快照事务内分批写入，事务内不发送邮件。
3. 发送前重新检查订阅者仍处于 verified 且未退订；冻结后新订阅者不加入本次活动。已退订或已失效收件人记录为 `skipped`，不遗留永久 pending。
4. 恢复发送消费 pending，失败重试消费 failed，二者共用发送执行逻辑但不混淆目标集合。任何路径都排除已记录为 sent 的投递。
5. 保留活动领取的条件更新，并让恢复和结束写入也使用状态条件，不能以无条件 update 覆盖其他发送者。恢复不是强制抢占；人工恢复前必须确认旧发送执行已停止，不能仅凭页面超时认定其退出。
6. 每次准备调用发送适配器前，在数据库中原子写入 `sending`、新的 `attemptId` 和尝试开始时间，再调用适配器。成功后写 sent；明确未被接受的失败写 failed。超时导致结果不明时条件更新为 `unknown`；进程退出后，由确认旧执行已停止的恢复操作把遗留 sending 转为 unknown。状态写入须匹配当前 attemptId，避免旧尝试覆盖后续尝试。
7. 从完整投递集合计算活动结果，不能只根据本轮实际调用数量决定是否失败。后台显示待发送、成功、失败、跳过及待核对数量，并区分继续未完成投递与重试失败投递。
8. unknown 不参与自动发送或失败重试。管理员核对结果通过下述独立操作写入，不借“恢复活动”批量把 unknown 改成 pending。核对操作本身不发送邮件。

**unknown 的证据与退出协议**

当前 [newsletter-mailer.ts](../../src/lib/newsletter-mailer.ts) 只有 `log/noop` 结果，没有可查询的真实提供商回执。[NewsletterDelivery](../../prisma/schema.prisma) 也未保存提供商消息标识。不能把本地 `log` 输出、客户端自行生成的 Message-ID、单纯超时或“查不到记录”当作真实上游已接受或未接受的证据。本项不顺带建设 SMTP 提供商或自动对账平台；核对能力按实际可得证据运行，无证据时保留 unknown 或明确放弃。

| 管理员决定 | 必需依据 | 投递状态转换 | 后续行为 |
| --- | --- | --- | --- |
| accepted | 能关联本次 attemptId 的上游接受回执或人工核实的提供商记录 | unknown → sent | 不再投递；sent 只表示上游接受，不保证进入收件箱 |
| not_accepted | 能关联本次尝试、明确证明上游未接受的拒绝记录 | unknown → failed | 后续显式失败重试才可发送，且再次检查是否退订 |
| abandon | 管理员明确放弃继续处理的理由，不推断实际是否发送 | unknown → skipped | 不再自动投递，保留放弃原因及不确定结果 |
| 证据不足且未决定放弃 | 无可支持上述决定的依据 | 保持 unknown | 持续显示待核对，不声称活动已经完成 |

- 新增 `POST /api/admin/newsletter/campaigns/[id]/deliveries/[deliveryId]/reconcile`（拟新增）。要求 `requireAdminSession`，校验投递属于该活动。输入包括所观察的 attemptId、上述三个可执行决定之一、原因及证据引用；accepted/not_accepted 必须提供可关联本次尝试的证据，abandon 必须明确确认放弃。响应说明状态与活动计数，不能仅返回笼统成功。
- 证据只保存必要的来源、关联标识与结论，不保存邮件正文、认证信息或敏感原始回执。可信的接受时间存在时用于 sentAt；没有精确时间则不伪造，核对时间单独记录。尚未接入提供商回执时，不虚构自动查询结果；隔离测试用可控适配器提供证据，log 的模拟成功不作为真实邮件送达证明。
- 补充投递的 attemptId、尝试时间及可选提供商消息标识等证据字段。新增专用 `NewsletterDeliveryReconciliation` 核对记录，保存 deliveryId、attemptId、决定、原因、证据引用、操作者及核对时间，以 `(deliveryId, attemptId)` 唯一约束限制一次尝试只有一个最终核对决定。记录不覆盖、不靠可被容量清理的通用操作日志充当唯一证据。它是业务核对历史，不承担任务调度。
- 在完成下述停发维护前置条件后，核对事务按固定顺序锁定活动和投递，重新检查活动不为 SENDING，再按 `deliveryId + status:unknown + attemptId` 条件更新。投递状态、核对记录和活动聚合结果一并提交；审计写入失败则全部回滚。sending、终态投递、活动归属不匹配或尝试已被替换均不能被旧操作覆盖。
- 相同 attemptId、决定、原因和证据的重复请求返回已有核对结果，不重复写审计、不发送邮件；不同决定、原因或证据竞争时仅一个提交，其余返回 409。旧 attemptId 的重放最多返回历史决定及当前状态，不能改变后来重试的结果。核对后若还有 unknown，活动保持 PARTIAL_FAILED；否则按完整投递集合重新聚合，不能只根据本行变更写 SENT。
- 人工恢复和核对均受“旧发送执行已停止”的操作前置条件限制。维护时暂停发送入口并结束旧执行，再开放核对；活动仍为 SENDING 时拒绝核对。仅有状态条件不构成跨实例安全抢占，本项不引入租约机制来作此保证。

**状态约定**

| 当前情况 | 后续行为 | 活动结果 |
| --- | --- | --- |
| DRAFT 且未冻结 | 领取并冻结集合，再发送 pending | SENDING |
| 执行中断且存在 pending | 旧执行停止后恢复，继续 pending | PARTIAL_FAILED → SENDING |
| 存在 failed | 显式重试失败集合，保留 pending 集合 | FAILED/PARTIAL_FAILED → SENDING |
| 存在 unknown | 不自动重发；按证据核对为 sent/failed，或审计后放弃为 skipped | PARTIAL_FAILED，直至核对后的全量聚合满足其他条件 |
| 无 pending、sending、failed、unknown，至少一封 sent | 本次活动结束；其余 skipped 仍展示原因和数量，不计为成功投递 | SENT |
| 无 pending、sending、unknown 且没有 sent，仍有 failed、全部 skipped 或集合为空 | 记录对应原因，不伪报发送成功 | FAILED |
| 同时存在 sent 与未完成或失败项 | 继续提供对应恢复、重试或核对入口 | PARTIAL_FAILED |

执行器仍持有发送权时活动保持 SENDING。执行结束或人工核对时，聚合按以下优先级计算：存在 pending/sending/unknown 为 PARTIAL_FAILED；否则存在 failed 时，有 sent 为 PARTIAL_FAILED、无 sent 为 FAILED；否则有 sent 为 SENT；剩余空集合或全部 skipped 为 FAILED。这样混合 failed/skipped、仅 pending 或仅 unknown 的集合也有确定结果。

**数据迁移与发送保证**

- 当前 delivery.status 为字符串，新增取值仍须同步类型、统计、API 和 UI。`audienceFrozenAt`、attemptId、证据字段及核对记录使用新增可空字段/新表的兼容迁移，不伪造历史提供商消息标识。先暂停活动发送并确认旧执行停止，再部署迁移和全部读写路径；新流程启用后的发送尝试必须有 attemptId。
- 历史活动没有完整收件人快照，不能用“当前所有 verified 用户”伪造原始集合。已发记录保留；未完成旧活动先导出已发集合，再由运营确认剩余名单，按确认名单修复或新建活动。
- 提供商支持幂等键时，使用稳定的 campaign + subscriber 标识；attemptId 只标识本地一次尝试，不替代提供商幂等键。SMTP 接受与本地提交之间不能保证严格一次；unknown 核对用于处理这一边界，不能把网络超时一律当作未发送。历史投递若无真实尝试标识，走独立的人工数据修复清单，不能编造 attemptId 后假装完成历史证据核对。
- 回退前停止发送并检查新状态和冻结字段，旧版本不具备解释这些记录的能力。不得删除投递历史来恢复运行。

**验收**

- 两名收件人，第一封已提交 sent、第二封未尝试时退出；恢复只发送第二封。
- pending 和 failed 同时存在时，继续发送不丢失 failed，失败重试不丢失 pending；只剩 sent 时操作不把活动改成 FAILED。
- 重复点击、并发领取和重复恢复不重新发送已记录 sent 的行。对旧执行尚未停止的场景不声称支持安全抢占。
- 冻结后退订不发送，冻结后新增订阅者不加入；空集合和全部 skipped 有明确结果。
- 在邮件接受后、本地 sent 提交前中断，旧执行停止后遗留 sending 转 unknown。有接受证据时核对为 sent，后续恢复和失败重试都不再发送该行；活动没有其他未完成项时进入 SENT。
- 分别覆盖有明确未接受证据转 failed、后续显式重试成功，以及无证据保留 unknown、管理员放弃转 skipped。无证据时不得自动重发；全部放弃且没有 sent 时按约定进入 FAILED，并展示原因。
- 重复和并发核对只提交一条决定；冲突决定返回 409。核对后重试产生新 attemptId，再重放旧核对请求，断言新尝试不受影响。测试核对与恢复/发送并发，活动计数不能丢失或提前进入 SENT。
- 投递、核对审计和活动聚合任一写入失败时全部回滚。补测未登录 401、非管理员 403、跨活动投递、缺少理由/证据、未知决定、SENDING 活动及非 unknown 投递，错误请求不改变数据。验收必须覆盖核对后的最终状态，不能停在“进入待核对”。

### P2-04：评论父子关系限定在同一文章

**入口与原因**

[评论 POST](../../src/app/api/comments/route.ts)验证目标文章，但未验证 `parentId` 对应评论的文章归属。公共读路径按父子关系展开时可能把回复展示到另一文章。

**实施方案**

1. 在业务校验层统一验证父评论存在、未软删除、属于同一文章，并满足可回复的公开审核状态；匿名请求不能向未公开父评论追加回复。顶层评论不受父评论检查影响。
2. 校验和插入放入同一事务；锁定父评论及目标文章，或使用能确保检查与插入一致的数据库约束。单独做事务外查询不足以防止软删除竞争。父评论 postId 不允许通过其他写入口任意变更。
3. 父评论删除、审核变化后的回复展示策略沿用既有审核规则；读取时同时约束父子双方 postId、软删除及公开状态，避免历史异常数据继续串入其他文章。
4. 错误经 `ValidationError` 或 `NotFoundError` 与 `toErrorResponse` 返回。对不可见父评论不给出其正文或其他私有信息。通知在成功提交后发送。

**数据与验收**

- 只读审计现存父子 postId 不一致的记录。列出 ID、归属和数量，由人工决定隐藏或解除回复关系；不静默修改文章归属或删除正文。
- 同文章、已公开的父评论允许回复；跨文章、不存在、已删除、未公开父评论拒绝且不插入。
- 测试父评论并发删除、审核状态变化、文章下线和读取历史异常关系；任何结果都不能跨文章展示。

### P2-05：文章更新复用创建时的 slug 校验

**入口与原因**

[validation.ts](../../src/lib/validation.ts) 的 `parsePostPatchInput` 对 slug 仅调用 `readString`，而创建使用 `assertSlug`。`foo/bar`、`foo?bar`、`foo#bar` 可形成不可按预期访问的路径。

**实施方案**

1. PATCH 提供 slug 时复用与创建一致的长度和格式检查；未提供时保持原值。空值、空白和类型错误使用现有输入契约处理。
2. 查全管理员编辑、AI 应用及其他改写 slug 的服务端入口，使最终写入都受同一规则约束。客户端提示只改善交互，服务端为权威边界。
3. 保留唯一冲突的 409 语义，不把数据库异常吞成校验成功。合法改名同步失效旧、新文章路径及相关索引缓存。
4. 对历史非法 slug 只产出清单及建议映射；公开 URL 修复需显式确定目标 slug 和重定向策略，不能在普通 PATCH 中悄悄归一化旧值。

**验收**

- 创建和更新对同一组合法、非法、超长 slug 得出一致结果；更新非法输入返回 400 且数据库不变。
- PATCH 不含 slug 时不改 slug；合法同值更新成功，冲突值返回 409。
- 合法改名后新路径可用，旧路径按现有页面语义处理；若实施历史 URL 修复，则单独验证批准的重定向映射。

### P2-06：标签页按活跃标签 ID 查询文章

**入口与原因**

[taxonomy.ts](../../src/lib/taxonomy.ts)按未删除标签解析 slug，而 [posts.ts](../../src/lib/posts.ts)的关系条件仅使用 slug。软删除后的 slug 可被新标签复用，旧关联仍可能混入新标签页。

**实施方案**

1. 入口先把 slug 解析为当前活跃标签 ID。后续文章列表与数量查询均使用该 ID，并保留文章已发布、未删除及标签活跃条件。
2. 列表、总数、分页和推荐等直接消费者共用同一语义的筛选条件，避免只修列表导致页数仍不正确。检查同类分类、系列路径，但仅在发现相同缺陷时另记范围。
3. 找不到活跃标签时沿用现有未找到语义；不能退化成无标签限制的全站列表。旧标签的历史关联不自动迁移到新标签。

**验收**

使用真实 PostgreSQL 建立旧标签及旧文章，软删除标签，再创建相同 slug 的新标签及新文章。新标签页只返回新标签关联文章；数量和多页结果一致。验证未发布、已删除文章仍被排除，以及标签不存在、再次软删除的路径。

### P2-07：日志容量清理移出请求路径

**入口与原因**

[api-operation-logs.ts](../../src/lib/api-operation-logs.ts)和[日志设置模块](../../src/lib/api-operation-log-settings.ts)把保留清理放入同步日志处理。请求成本包含清理扫描；目前没有压测结果，方案不预设性能提升百分比。

**实施方案：按 Issue #2 执行**

1. 每次请求仍同步完成一次日志 INSERT，移除请求路径上的容量扫描、排序和删除。保留原有错误处理语义，不新增异步队列或 outbox。
2. 容量清理由一个共享 maintenance runner 负责。Cron 和管理员手动维护调用同一 runner；修改容量设置只保存配置，不触发清理。
3. 使用 PostgreSQL advisory lock 排除重复维护。锁和受保护查询必须绑定同一实际连接或事务，不能在连接池中用互不关联的请求假装持锁。
4. 沿用现有从新到旧累计行字节数、识别超限记录的语义；按稳定的时间、ID 顺序从最旧超限行中每批最多删除 1,000 行。不得用全表大小、估算行数或只按时间截断替换这个口径。
5. 返回 `completed`、`more_remaining` 或 `skipped_locked`，包含触发来源、容量上限、批量上限、运行前后行数与字节数、删除行数、剩余超限字节和耗时，不包含日志敏感明细。大积压通过后续成功批次收敛，不在一次 Web 请求内循环清空全库。
6. 受保护 Cron 路由只使用 `CRON_SECRET`；在 middleware 精确路径注册表登记，handler 再校验，遵循缺配 503、错误 401 和限流契约。GitHub Actions 每 15 分钟调用。管理员手动维护继续使用管理员会话鉴权。
7. 原有手动删除 30/60/90 天日志行为不变。无新增 UI、清理历史表、schema 迁移或 #3 前置依赖。

**验收与运维**

- 请求记录日志只执行约定的 INSERT，不扫描或删除保留数据；配置保存也不启动清理。
- 真实 PostgreSQL 验证不同行大小、相同时间戳、恰好达标、超过 1,000 行积压及最旧行先删；重复运行最终达到容量限制。
- 两个 runner 并发时一个执行、一个返回 skipped_locked；持锁执行失败后锁可释放，无误删或超批量删除。
- 验证 Cron 鉴权、精确路由注册、定时间隔与管理员入口复用。Cron 连续失败意味着容量暂时不收敛，应由工作流失败状态暴露，不能宣称容量始终受限。
- 先部署共享 runner 与请求路径改造，再启用受保护入口和定时工作流；启用前可用管理员入口验证一批。回退先停用工作流，再回退应用。旧版本若恢复请求内清理，原扫描开销也会恢复；已按策略删除的日志不会恢复，上线前确认保留配置正确。

- 在 `pnpm build` 后的生产服务预热目录、分类或标签页和文章页，执行改名或删除，再访问验证已刷新，无需等满 300 秒。不能只用 dev server 验证 ISR。
- 回归既有公共页面缓存契约；和 P2-06 联合验证标签 slug 复用后不会继续显示旧标签文章。

### P2-09：AI 活动同步使用可变化的业务快照

**入口与原因**

[批次 GET](../../src/app/api/admin/ai/batch/route.ts)仅返回 `{ success: true }`，[AiTaskActivitySync.tsx](../../src/components/admin/ai/AiTaskActivitySync.tsx)只能生成固定 `no-status` 签名。摘要状态不变时，批次的后续变化无法触发 `router.refresh()`。

**实施方案**

1. 为当前页面关注的批次返回精简快照，包含稳定任务 ID、业务状态、计数及由业务变化驱动的版本信息。排序固定，不包含响应生成时间或其他每轮变化的字段。
2. 纳入刚刚结束的被观察任务，不能查询“当前活动任务”后丢掉其终态；也不能只比较总数，否则不同任务的完成与新增相互抵消。限定请求 ID 或有明确边界的任务集合，避免每十秒扫描任务全表。
3. 每条状态请求使用完整 URL 字符串作为 SWR key，配合共享 `apiFetcher` 和既有轮询节奏，再组合已取得的业务快照。只有业务签名变化才刷新；没有活动任务时停止轮询。请求失败不能冒充成功的稳定状态。
4. 单一路径错误允许其他快照继续更新，管理员 401 仍须交给全局认证处理并保留真实 API URL。若保留结果聚合逻辑，不得通过 `Promise.allSettled` 吞掉认证错误；局部 onError 必须先调用现有 `handleGlobalSwrError`。
5. P2-02 确定终态含义后再锁定快照契约。本项只修复状态可见性，不新增执行副作用。当前旧 resume 行为的彻底移除随 #8 进行；#8 发布后，所有 GET 与 UI 轮询必须纯读。

**验收**

- 只有 AI 批次活动、摘要空闲时，QUEUED → RUNNING → 终态均能刷新；最终无活动任务时停止轮询。
- 相同快照重复轮询不刷新；任务 ID 变化但总数相同仍能刷新；完成任务不会因退出活动集合被遗漏。
- 单路径异常不阻断另一条路径；401 仍触发统一登录处理。
- SWR 测试隔离缓存，不为通过测试修改生产 dedupingInterval。完成 #8 后再断言状态查询不会启动任务。

2. 模型用例复用现有 `withMockAiModel` 的作用域管理能力；需要测试模型创建 UI 时，注册 UI 返回的模型 ID 供清理，不用 API 创建代替被测 UI 动作。
3. 夹具获取后立即进入 `try/finally`，按依赖顺序清理：等待相关后台执行结束，清理本用例任务和内容，再删除模型，最后关闭上游。
4. 只清理本用例创建的 ID，不按宽泛前缀删除共享数据。清理失败必须进入测试报告；测试主体也失败时保留原失败并同时记录清理错误。
5. 数据库软删除行为须计入夹具策略：仅隐藏测试文章不足以声称无残留。物理清理仅针对隔离测试数据库内明确归属的测试数据。

**验收**

- 在一次性数据库连续运行两次，均通过且每轮结束无本次拥有的文章、关系、模型和任务残留。
- 在文章创建后、模型创建后及断言失败时注入异常，仍清理本用例已知资源；清理错误可见。
- 原有数据与既有 PR #22 夹具保持不变，不通过扩大删除范围让测试通过。

## 4. 实施完成的共同门槛

1. 每个修复先有能失败的行为回归，再验证修复结果。数据库约束、事务、锁与软删除用真实隔离 PostgreSQL 验证，不能只依赖 Prisma mock。
